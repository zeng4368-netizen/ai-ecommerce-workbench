# 行动中心：从候选到人工复盘

入口：http://127.0.0.1:8765/#tasks 。需要本地 Python 服务。原 Skill 文件、公式、表头未修改。

## 日常使用

1. 点击「同步当前数据候选」。系统按当前会话数据生成合并候选，冻结证据。重复同步同一快照不会重建；数据或规则变化创建新版本，不把旧任务的完成状态套到新问题。
2. 筛选模块，打开优先任务，先查看来源、规则和逐条证据。当前仍是历史数据，不可当作实时店铺异常。
3. 点击「让 AI 拟定行动方案」。DeepSeek 只收到这一任务的证据摘要，返回假设、步骤、验收条件、一个主要核查指标、风险护栏和缺失数据。调用消耗 API 额度，不自动重试。
4. 审核 AI 草案后点击「采用到编辑区」。这一步不改变任务阶段。可编辑步骤、验收条件和指标；补充负责人、截止日期、实时基线及风险护栏。
5. 勾选人工复核确认，点击「确认入列」，再点击「开始处理」。工具不会自动修改广告、发起采购或联系达人。
6. 线下完成核查或经授权的业务处理后，填入实际处理记录、结果证据（文件路径/报表编号/记录）、观察结果，点击「提交验收」。这里只记录证据引用，不自动上传或验证文件真实性。
7. 人工复核并填写复核人、结论和说明。结论可以是支持原假设、不支持、证据不足。点击「人工验收并归档」结束本轮工作；不把“操作完成”当作“产生收益”。

新任务必须具备负责人、截止日期、行动、验收条件、指标、基线及护栏才能入列。不能跳过执行证据直接完成。变更已批准的行动/指标/验收口径后需要重新确认。搁置、退回、重开都需填写原因；重开清空本轮结果字段，历史仍在审计轨迹中。

## 候选规则

| 模块 | 新工作流的候选规则 |
|---|---|
| 广告 | 沿用既有风险判断，P0/P1入选；同店铺、商品ID、币种和问题类型合并，每条广告原值保留，不混用素材、计划和商品口径 |
| 库存 | 保留可售天数1–14的核查；补充ERP已匹配、可用库存≤0且7日均销>0的候选，不等于断货损失已发生 |
| 达人 | 保留GMV≥100 RM且退款金额占比≥10%；取消旧版最多4人的展示截断，小样本先查证，不据此永久停止合作 |
| 结算 | 新增同店编同款账单结算合计−成本合计<0且成本>0的核查；仅为账单口径差额，非完整净利润；记录数不是订单数 |

初始数据形成94个合并候选：广告27、库存36、达人20、结算11。此数不是原看板风险SKU总数。全量候选保存在SQLite，页面分批展示，可按模块、阶段、商品/负责人和逾期状态筛选。

## 安全与可追溯

- 模型无业务执行工具，只返回结构化JSON草案。服务端校验字段结构和证据ID；这不证明模型的事实推理一定正确。
- 模型不能改变冻结证据、任务原优先级或自动批准入列。失败/无效的模型回复保留记录，但不覆盖已采用方案。
- 每次保存和状态变化都有时间、版本和字段差异；并发编辑版本不符会拒绝覆盖。
- AI原文、输入证据、模型、Token和输入哈希可回查。API Key仅在本机.env。
- 脱敏演示模式下新行动中心只读，详情和导出关闭，以免编辑记录或证据泄露原名。需展示操作时先自行确认数据适合展示，再关闭脱敏。
- 旧版待办状态保留在原表，可从「查看旧版进度」访问。不自动将旧版“已完成”迁移为新工作流“已复盘”。
- 无多用户登录或真实权限体系；负责人/复核人为本地记录字段，不是已认证身份。它是单机工作台，不应开放到公网。
- 目前验收由人判断，没有统计显著性或自动业务收益核验。前后数据变化不能直接证明因果。

## 技术位置

- `assets/action-candidates.js`：独立候选层，不修改原算法。
- `assets/action-center.js` + `assets/actions.css`：行动看板与处理表单。
- `action_center.py`：SQLite状态机、并发版本校验、AI草案、审核关卡。
- SQLite：`actions` / `action_events` / `action_ai` 三张新表，旧 `state` 和 `analyses` 表保留。

复盘设计参考 ab-testing skill 的指标、基线、护栏和结论边界；本工具没有自动声称A/B测试显著或计算收益提升。
